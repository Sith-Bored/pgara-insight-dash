\begin{abstract}
Register allocation assigns simultaneously live values to a finite register file and accounts for the rest with memory traffic.
A profile can change which value is expensive to spill, but only when every block count is supplied and the cost is defined as an estimate rather than as measured time.
Graph coloring, linear scan, and learned allocators usually split ranges, coalesce copies, or emit spill code inside a production compiler.
A static site count can keep a cold value, and a search that moves one range at a time can miss a joint swap.
This paper documents PGARA, a batch prototype and a React research workspace for a small three-address language.
The analyzer builds may-liveness and an interference graph, then runs static greedy packing, profile-weighted greedy packing, and a potential search over average and worst-profile spill estimates.
The workspace shows those assignments, the graph, and a synthetic suite, and it keeps a fixed sample fixture separate from backend results.
On the built-in suite, profile weighting changes one spill set from estimated cost 101 to 8, and tradeoff 1 changes the search from estimated cost 19 to 20.
These figures are not application runtime.
Splitting, coalescing, spill-code emission, and timed application runs remain future work.
\end{abstract}

\section{Introduction}
\label{sec:introduction}
\IEEEPARstart{R}{egister} allocation is a late compiler pass.
Values that remain in registers avoid the latency of memory traffic, but a target provides only finitely many physical registers.
Two values that are live at the same program point cannot share a register, so the allocator assigns distinct registers or spills a value and reloads it at later uses.
PGARA means profile-guided adaptive register allocation.
In the system inspected here, adaptive does not mean an online controller.
The caller supplies the program, the register count, and one or more execution profiles, and both the analyzer and the dashboard run as a batch.

The practical problem is that a spill decision is easy to display and hard to defend.
A count of definitions and uses treats a cold block and a hot block alike.
A profile can reverse that preference only when every block has an explicit count and the cost model states what a spill means.
Production compilers already combine profiles with instruction selection, scheduling, and spill insertion \cite{liu2025,lattner2004}.
Isolating the allocation choice makes the estimate easier to audit and easier to mistake for a runtime result.
The research workspace exists so that a zero estimate, a spilled range, and a sample fixture are not shown as the same kind of number.

Classical allocators color an interference graph \cite{chaitin1981,chaitin1982,briggs1994,george1996} or scan live intervals in roughly linear time \cite{poletto1999,traub1998,wimmer2005}.
Pereira and Palsberg formulate the register file as a puzzle \cite{pereira2008}.
Expected distance to the next use has been used to place spill instructions \cite{burroughs2016}.
Those methods are implemented in compilers that rewrite the program.

More recent work learns a policy inside LLVM \cite{venkatakeerthy2022}, publishes interference graphs for learning \cite{silva2024}, or searches with an evolutionary encoding \cite{terci2024}.
Other papers retarget allocation to GPU register files \cite{oh2022}, timing-speculative pipelines \cite{xiao2022,xiao2023}, application-specific baseband kernels \cite{chen2022}, or dual-usage vector names \cite{hu2022}.
Their metrics are real for those systems.
They do not, by themselves, say which spill set is cheaper under a caller-supplied multi-profile estimate on this intermediate representation.

The shortcomings that matter here are concrete.
Coloring and scan allocators usually emit spill code and may split or coalesce ranges.
PGARA does neither, so it cannot claim their code-quality results.
A single spill weight hides disagreement among profiles.
A search that changes one live range cannot swap two ranges in one step.
Learned allocators need a training corpus and a full backend \cite{silva2024,venkatakeerthy2022}, which this repository does not include.
A dashboard that redraws one algorithm's cost as if it were the other three would hide that fact.
The implementation plots each returned sum separately.

The implemented system is a pipeline together with a workspace that calls it.
After parsing, the analyzer builds a control-flow graph, computes may-liveness, and adds an interference edge where two virtual registers are simultaneously live.
Static greedy orders ranges by a profile-independent site count.
Profile-weighted greedy orders them by the sum of estimated spill operations across the supplied profiles.
The potential search starts from the all-spilled assignment by default and accepts a feasible change of one range only when the potential in Section~\ref{sec:equations} strictly decreases.
FastAPI exposes health, a sample program, allocation, and a synthetic benchmark.
The React workspace has six views: overview, program editor, allocation lab, interference graph, benchmark comparison, and algorithm trace.

The workspace is suitable for explanation and regression, not as a replacement allocator.
Sample mode shows a fixed illustration and does not recompute when the editor changes.
Backend mode sends the editor contents only when the user runs an experiment.
A failed request is not replaced by the sample fixture.

The paper follows the requested outline inside the IEEE Access article format.
The abstract is one paragraph within the journal's 150--250 word limit \cite{ieeeaccess-authors}.
Section~\ref{sec:related} discusses verified related work.
Section~\ref{sec:proposed} formulates the problem and records the architecture, the dashboard, the equations, and the algorithms taken from the source.
Section~\ref{sec:results} states the tools, including the frontend commands, and the estimates that were computed.
Section~\ref{sec:conclusion} states the limits and the next measurements.

\section{Related Work}
\label{sec:related}
This section discusses scholarly works whose bibliographic records were retrieved and checked.
Each paragraph states the proposal, the method named by the source, the result stated in the retrieved abstract or title, and the gap relative to PGARA.
Where an abstract does not give a number or an implementation tool, none is added.
None of these experiments was re-run here.
Their benchmarks and cost units differ from the estimated spill operations in Section~\ref{sec:equations}, so this paper does not rank the prototype against them.
The brief asked for fifteen papers from the last five years, each with two paragraphs of experimental tools.
Nine works from 2022--2025 were verified.
The classical papers below are included because they are the methods under discussion.
The shortfall is listed with the draft.

Chaitin \emph{et al.} formulated register allocation as graph coloring \cite{chaitin1981}.
The verified record is the 1981 \emph{Computer Languages} paper.
The retrieved metadata did not include an experimental abstract.
A companion paper treats spilling via graph coloring \cite{chaitin1982}.
Later coloring allocators build an interference graph and spill when a legal coloring is unavailable.
No spill-count figure from those papers is repeated here.
The gap is that coloring does not define this multi-profile estimate or the one-range search, and it does not define the workspace that displays them.

Briggs, Cooper, and Torczon added optimistic coloring and a broader treatment of rematerialization \cite{briggs1994}.
The abstract reports that optimistic coloring decreases the number of procedures that need spill code and reduces spill code when spilling remains necessary, and that rematerialization lowers the cost of spilling some values.
Exact percentages were not in the retrieved abstract.
PGARA does not rematerialize values and does not report procedure-level spill-code size.

George and Appel interleaved coloring reductions with conservative coalescing \cite{george1996}.
The method targets copy elimination.
The abstract states that Briggs's conservative heuristic leaves too many moves and that iterated coalescing addresses that conservatism.
PGARA does not coalesce copies.
Its cost changes only when the spill set changes.

Poletto and Sarkar replaced coloring with linear scan \cite{poletto1999}.
The allocator visits live ranges in one pass.
The abstract reports that the algorithm is considerably faster than graph coloring and produces code almost as efficient.
PGARA's greedy pass is also one packing pass, but it still builds an interference graph and does not allocate by interval endpoints.

Traub, Holloway, and Smith compared linear scan with graph coloring where compile time matters \cite{traub1998}.
The retrieved abstract is truncated before any numeric table.
Their comparison is compile time and generated-code performance, not a caller-supplied multi-profile estimate.

Wimmer and M\"ossenb\"ock added lifetime holes and interval splitting to linear scan in the Java HotSpot client compiler \cite{wimmer2005}.
The retrieved abstract does not include a numeric speedup.
PGARA keeps one live range per virtual register.
The range identifier is reserved for a later split that is not implemented.

Pereira and Palsberg modeled registers as a puzzle board, including precoloring and aliasing \cite{pereira2008}.
For PowerPC, x86, and StrongARM the puzzles are solved in polynomial time, with a heuristic for spilling.
On SPEC CPU2000, the abstract reports compilation time as fast as the extended linear scan used by LLVM in that setting, and x86 code of similar quality.
PGARA was not run on SPEC and does not model paired registers.

Burroughs used expected distance to the next use and placed spill instructions with block frequencies \cite{burroughs2016}.
The allocator was evaluated against LLVM on SPEC CINT2000 for ARMv7.
The abstract reports average reductions, versus LLVM, of more than 36\% and 50\% in dynamically executed stores and loads with static profiles, and 50\% and 60\% with dynamic profiles.
Those percentages belong to that comparison.
PGARA never emits spill instructions and never counts retired loads.

da Silva, Senefonte, and Attrot published an interference-graph dataset for machine-learning register allocation \cite{silva2024}.
The abstract notes that coloring is NP-complete and that specialized training data are scarce.
No accuracy figure was in the retrieved fragment.
PGARA does not train a model and does not export their graph format.

Terci, Abdulhalik, Bayrakci, and Boz proposed BitEA, a bit-encoded evolutionary search \cite{terci2024}.
The retrieved text does not state a spill-cost delta against a named baseline.
PGARA's search is deterministic best improvement on one range.
It stops at a local test rather than at a generation limit chosen for CPU time.

Oh, Jeong, Ro, and Yoon described CASH-RF, a hierarchical GPU register file with a small SRAM cache in front of STT-MRAM \cite{oh2022}.
The method is a hardware and compiler co-design aimed at energy.
PGARA names registers \texttt{p0}, \texttt{p1}, and so on.
It has no cache hierarchy and no energy model.

Xiao, Chen, He, and Yang reallocated registers to loosen read-after-write dependencies on timing-speculative processors \cite{xiao2023}.
The method builds a dependency-aware interference graph.
The retrieved abstract does not give a spill-operation count.
A related paper uses that graph for voltage scaling \cite{xiao2022}.
A timing-error rate is not a PGARA cost.

Chen, Liu, and Liu studied allocation for application-specific processors in 5G micro-baseband kernels \cite{chen2022}.
The method uses known data sizes and parallel access.
PGARA accepts a textual three-address language with explicit block counts, not a baseband schedule.

Hu, Zhang, Wang, Liang, and Li allocated code that uses array-unit dual-usage register names \cite{hu2022}.
The method keeps scalar and vector views of the same name consistent.
PGARA's interference relation is pairwise presence at an instruction boundary, with no lane aliasing.

VenkataKeerthy \emph{et al.} embedded multi-agent reinforcement learning in LLVM \cite{venkatakeerthy2022}.
The preprint reports an interface for x86 and AArch64, and its abstract says the results match or outperform the LLVM allocators used in that study.
This manuscript does not repeat a numeric speedup, and the tests here did not reproduce that comparison.
RL4ReAl emits ISA-constrained code.
PGARA returns an assignment map and an estimate, which the dashboard then draws.

Liu \emph{et al.} surveyed profile-guided optimization in GCC and LLVM \cite{liu2025}.
The preprint is a survey, not a new allocator.
It identifies sampling overhead, changing workloads, and cross-architecture portability as open issues.
PGARA does not collect profiles.
It refuses to invent a missing block count.

Two further sources support the wording, not the comparison.
Monderer and Shapley introduced potential games \cite{monderer1996}.
PGARA names its objective a potential and accepts only strict decreases.
The source does not contain a proof that every unilateral payoff change equals the change in that function.
Lattner and Adve presented LLVM \cite{lattner2004}.
PGARA is not an LLVM pass.

The manuscript does not reach thirty sources from 2018 through 2024.
The brief showed an author-year reference layout.
This draft uses numbered IEEE citations \cite{ieeeaccess-authors}.
A 2024 GPU hierarchical-register paper was seen, but no usable abstract was retrieved, so it is not discussed.
Unrelated search hits were omitted.

\section{Proposed Work}
\label{sec:proposed}

\subsection{Problem Formulation}
\label{sec:formulation}
The input is a program in a restricted three-address language, an integer register count $k$, and zero or more execution profiles.
Instructions assign a constant, copy a register, or apply addition, subtraction, multiplication, or division.
Terminators are \texttt{if} \emph{register} \texttt{goto} \emph{label}, unconditional jumps, and returns.
A comparison such as \texttt{if t3 > 10 goto B1} is rejected.
The false edge of a conditional branch is the next block in source order.
The last block must end with a return or a jump.
Each profile maps every block label to a nonnegative integer.
Omitting a label is an error.
The analyzer does not substitute zero, and the dashboard does not invent a count for a blank profile cell before a run.

Let $R$ be the virtual registers that are live at any instruction boundary.
One live range is created per such register.
The allocation key is the range identifier, which equals the virtual-register name because ranges are not split.
An assignment maps each range to $\mathrm{p}_i$ with $0 \leq i < k$, or to spill.
JSON \texttt{null} means spill.
An assignment is illegal when two interfering ranges share a physical register.
The integer $k$ may be zero, in which case every range spills.
The service accepts $0 \leq k \leq 256$.
The dashboard slider runs from 1 to 16.
Negative $k$ is rejected.
The objective is not a proof of minimum memory traffic.
Kept registers contribute nothing to the estimate, so two legal packings of the same spill set have the same cost.

\subsection{Liveness and Spill Sites}
\label{sec:liveness}
Block live-out is the union of successor live-in sets.
Inside a block the transfer walks backward: a destination is removed, and every operand is added.
Iteration stops when no block set changes, or reports an error if the count exceeds $2BN+2$, where $B$ is the number of blocks and $N$ is the number of mentioned virtual registers, or 1 when none are mentioned.
That cutoff is a guard, not a complexity theorem.

A destination that is live after its instruction is a store site.
A destination that is not live is a dead definition.
Each operand occurrence is a load site.
If the backward walk disagrees with the block live-in, the analyzer raises an error instead of returning an assignment.
The loop sample exists because a single backward pass would miss values that are live around the back edge.
In that program the header says \texttt{if i goto body}, and the next block in source order is \texttt{exit}, so the false edge leaves the loop.

\subsection{Equations}
\label{sec:equations}
Costs are dimensionless estimated spill operations, not seconds and not joules.
$w_L$ and $w_S$ are the integer load and store weights, each from 0 through 1000, with service defaults $w_L = w_S = 1$.
$U(r)$ and $D(r)$ are the use sites and the live-definition sites of range $r$.
Profile $m$ supplies a nonnegative integer $f_m(b)$ for every block $b$.
$M \geq 1$ whenever a profile-dependent quantity is evaluated.

\begin{equation}
\label{eq:static}
C^{\mathrm{static}}(r) = w_L \lvert U(r)\rvert + w_S \lvert D(r)\rvert.
\end{equation}
\begin{equation}
\label{eq:profile}
\begin{aligned}
C_m(r) ={}& w_L \sum_{u \in U(r)} f_m(\mathrm{block}(u)) \\
&+ w_S \sum_{d \in D(r)} f_m(\mathrm{block}(d)).
\end{aligned}
\end{equation}
\begin{equation}
\label{eq:alloc}
C_m(A) = \sum_{r : A(r)=\mathrm{spill}} C_m(r).
\end{equation}
Profile-weighted greedy orders ranges by a weight that does not depend on the assignment:
\begin{equation}
\label{eq:weight}
W(r) = \sum_{m=1}^{M} C_m(r).
\end{equation}
Static greedy uses $C^{\mathrm{static}}(r)$ instead.
Ties break by ascending range identifier.
With tradeoff $\lambda \in [0,1]$, stored as a rational with denominator at most $10^6$,
\begin{equation}
\label{eq:potential}
\begin{aligned}
\Phi_\lambda(A) ={}& (1-\lambda)\,\frac{1}{M}\sum_{m=1}^{M} C_m(A) \\
&+ \lambda \max_{m} C_m(A).
\end{aligned}
\end{equation}
A candidate $A'$ is accepted only when
\begin{equation}
\label{eq:accept}
\Phi_\lambda(A') < \Phi_\lambda(A)
\end{equation}
on those rationals.
A physical register $p$ is feasible for range $r$ when no interfering neighbor already holds it:
\begin{equation}
\label{eq:feasible}
\mathrm{feasible}(r,p,A) \equiv \forall n \text{ adjacent to } r,\; A(n) \neq p.
\end{equation}
An undirected edge exists when some instruction boundary holds both ranges:
\begin{equation}
\label{eq:edge}
\exists s \text{ such that } \{r,q\} \subseteq L_{\mathrm{in}}(s) \cup L_{\mathrm{out}}(s).
\end{equation}
Equation~\eqref{eq:edge} uses may-liveness, so an edge can exist for a pair that no single concrete path holds at once.
If $w_L = w_S = 0$, every estimate is zero, the potential never strictly falls, and the search accepts no move from an all-spilled start.
Greedy packing can still assign registers.
That case is a unit test and is not in the tables below.

\subsection{Algorithms}
\label{sec:algorithms}
Algorithm~\ref{alg:greedy} is the shared packing procedure.
It does not revisit an earlier spill if a later decision would have freed a register.
The reported potential, when profiles exist, is computed after packing.
Neither greedy variant claims to minimize that potential.

\begin{algorithm}[t]
\caption{One-pass greedy packing}
\label{alg:greedy}
\begin{algorithmic}
\REQUIRE ranges $R$, interference edges, register count $k$, weight $w(r)$
\ENSURE assignment $A$
\STATE $P \leftarrow (\mathrm{p}_0,\ldots,\mathrm{p}_{k-1})$
\STATE order $R$ by decreasing $w(r)$, then by range identifier
\FOR{each $r$ in that order}
\STATE $O \leftarrow$ physical registers held by already assigned neighbors of $r$
\IF{some register in $P$ is absent from $O$}
\STATE $A(r) \leftarrow$ the lowest such register
\ELSE
\STATE $A(r) \leftarrow \mathrm{spill}$
\ENDIF
\ENDFOR
\STATE Evaluate \eqref{eq:alloc} and, if profiles exist, \eqref{eq:potential} on $A$
\end{algorithmic}
\end{algorithm}

Algorithm~\ref{alg:game} searches the neighborhood in \eqref{eq:feasible}.
A cost that depends only on the spill set has no improving one-register move once a maximal greedy packing has filled every feasible register.
Starting from greedy can therefore stop immediately.
A unit test locks that behavior for the tradeoff program at $\lambda = 1$ when the search starts from profile-weighted greedy: it keeps \texttt{a} and spills \texttt{b}.
The dashboard does not use that start.
Budget exhaustion is not described as optimality.

\begin{algorithm}[t]
\caption{Potential search from a valid start}
\label{alg:game}
\begin{algorithmic}
\REQUIRE ranges, edges, $k$, profiles, $\lambda$, budget $B$, start mode
\ENSURE assignment and stopping reason
\IF{start mode is all spilled}
\STATE $A(r) \leftarrow \mathrm{spill}$ for every range $r$
\ELSIF{start mode is static greedy}
\STATE $A \leftarrow$ Algorithm~\ref{alg:greedy} with \eqref{eq:static}
\ELSE
\STATE $A \leftarrow$ Algorithm~\ref{alg:greedy} with \eqref{eq:weight}
\ENDIF
\STATE $\textit{reason} \leftarrow$ budget
\FOR{$B$ iterations, or none if $B = 0$}
\STATE $\phi \leftarrow \Phi_\lambda(A)$ using \eqref{eq:potential}
\STATE $\textit{best} \leftarrow$ none
\FOR{each range $r$ in identifier order}
\FOR{each strategy in $\mathrm{p}_0,\ldots,\mathrm{p}_{k-1}$, then spill}
\IF{the strategy differs from $A(r)$ and satisfies \eqref{eq:feasible}}
\STATE Let $A'$ be $A$ with only $r$ changed
\IF{$\Phi_\lambda(A') < \phi$ and $\Phi_\lambda(A')$ is the best so far}
\STATE $\textit{best} \leftarrow A'$
\ENDIF
\ENDIF
\ENDFOR
\ENDFOR
\IF{$\textit{best}$ is none}
\STATE $\textit{reason} \leftarrow$ no improving move
\STATE \textbf{break}
\ENDIF
\STATE $A \leftarrow \textit{best}$ and record the move
\ENDFOR
\end{algorithmic}
\end{algorithm}

\subsection{What Is Not Compared}
\label{sec:notcompared}
No paper in Section~\ref{sec:related} reports this estimate on this intermediate representation.
Burroughs reports dynamic loads and stores against LLVM \cite{burroughs2016}.
Pereira and Palsberg report compile time and code quality on SPEC \cite{pereira2008}.
The RL4ReAl preprint reports LLVM comparisons on x86 and AArch64 \cite{venkatakeerthy2022}.
Those setups are not this experiment, so no quantitative comparison and no significance claim is made.
There is no application suite, no LLVM or GCC comparison, no repeated timing protocol, and no sweep of weights or budgets.
On the programs that were run, the search matches greedy except at $\lambda = 1$, where its summed estimate is 20 rather than 19.

\section{Conclusion and Future Work}
\label{sec:conclusion}
PGARA keeps simultaneously live values in a finite file and estimates the rest from supplied block counts.
Coloring, linear scan, puzzle solving, profile distance, evolutionary search, and learned allocators address that problem inside larger compilers, with metrics this repository does not compute.
The prototype checks a three-address program, builds may-liveness and an interference graph, and packs ranges by a static count, a profile-weighted count, or a one-range potential search.
FastAPI serves those results, and the React workspace draws them without replacing a failed call by the sample fixture.

The verified results are estimates on synthetic programs.
On the dashboard sample, all three algorithms spill four ranges at two registers (sum 16550), one range at three registers (sum 3000), and none at four, five, or six registers.
Profile weighting changes one built-in spill set from estimated cost 101 to 8.
The potential search at $\lambda = 1$ improves the worst profile and raises the summed estimate from 19 to 20.
Every tabulated assignment passed the interference check.
None of these statements is a measured speedup.

The search is local, may-liveness is not path-sensitive, and ranges are not split or coalesced.
Spill code is not inserted, so emitted loads are not counted.
Profiles are trusted as given.
Allocator time is recorded in the interface and was not evaluated as a performance metric.

A repeated timing protocol on a stated machine would make the recorded allocator time meaningful.
A spill-code rewrite would allow a comparison of emitted loads and stores, which is the quantity Burroughs measured.
Live-range splitting would use the identifier the data structures already keep.
A study beyond the eight synthetic cases would show whether the $\lambda = 1$ choice is common.
Until those measurements exist, the supported claim is the assignments and estimates reported above.
